# Dataset Card — ESP Flow-Feature Dataset

This describes the dataset used to train `app/ml/`'s traffic-type
classifier: `data/datasets/flow_features.csv`, built by
`python -m app.ml.dataset` from labeled pcaps in `data/pcaps/`.

## Status at time of writing (updated 2026-09-02)

**A real, small pilot dataset now exists** — 40 flow rows from 30 unique
real pcaps, captured against 5 of the 17 testbed configs (4 MODP-based
plus one AES-GCM/ECP one, after fixing the plugin gap described in
`backend/testbed/README.md`) across all 6 traffic types. This is
genuinely real: real strongSwan IKE negotiation, real ESP encapsulation,
real tcpdump captures, real `python -m app.ml.dataset` / `python -m
app.ml.train` runs, not synthetic fixtures.

**Read "Class balance" and "Real training result" below before citing any
number from this dataset** — 32 rows is enough to prove the pipeline is
correct end-to-end on real data, and not remotely enough to claim the
classifier generalizes. Scaling this up (more configs, longer capture
durations, more repetitions per class) is real, valuable, currently
unstarted work — not a formality.

## Provenance

Every row is derived from a pcap captured against the strongSwan testbed in
`backend/testbed/`, generated by `testbed/scripts/generate_traffic.py` and
captured by `testbed/scripts/capture.sh`. No packet payload is ever read —
every feature comes from ESP header fields (SPI, sequence number) and
observable packet size/timing, per `app/flow/features.py`.

**The pcap filename is the ground-truth label**, per the naming convention
in `CLAUDE.md`:
```
{mode}_{cipher}_{dh}_{pfs}_{iptype}_{traffic}_{timestamp}.pcap
e.g. tunnel_aesgcm256_dh19_pfson_ipv4_voip_20260901T1400.pcap
```
`app/ml/dataset.py::parse_label_from_filename` parses the `{traffic}`
segment directly — never re-derive or hand-correct a label after capture,
or the ground truth is broken.

## Config matrix

17 canonical IPsec configurations (mode × cipher × DH group × PFS ×
IP version × IKE version), spanning strong AEAD baselines down to two
deliberately weak/broken configs (3DES/MODP-768, AES-128/SHA-1/MODP-1024).
Full table with every config's parameters:
`backend/testbed/README.md#config-variants`.

The config itself is **not** a training label for the ML classifier — it
only affects what the IKE parser (a deterministic, non-ML component)
extracts. The config matrix's purpose in this dataset is to prove the
traffic-type classifier's features are robust to the encryption/DH/PFS
settings underneath — a real observer doesn't get to pick the config, and
the classifier shouldn't implicitly depend on one either.

## Traffic types (target classes)

| Class | Generator | Real or approximated |
|---|---|---|
| `icmp` | `ping` at ~20 pkt/s | Real |
| `web` | HTTP GET loop against a local server | Real |
| `voip` | ~160-byte UDP packets every 20ms (G.711-like) | Real (synthetic traffic pattern, not a real VoIP protocol stack, but a legitimate proxy for its known packet shape) |
| `video` | Bursty ~1400-byte UDP packets, MTU-sized majority | Real (same caveat as `voip`) |
| `email` | Irregular 800-4000 byte UDP bursts, 0.5-2s gaps | Real (same caveat) |
| `messaging` | Small (80-300 byte) bursty packets + a compressed periodic keepalive | **Approximated.** Cannot capture real WhatsApp (or similar) traffic in an isolated lab with no internet egress or real client pairing. This generator is tuned to WhatsApp's publicly known traffic characteristics (small bursty messages, periodic keepalives) but is not a real captured messaging-app protocol. **State this plainly if asked** — do not present `messaging` rows as real WhatsApp captures. |

`voip`/`video`/`email` traffic is generated as raw UDP with size/timing
shaped to match the named traffic type's known characteristics, rather
than running the literal application protocol (RTP/SIP, a real streaming
server, SMTP) end-to-end inside the lab. This is a deliberate scope
simplification for testbed complexity, not a hidden one — every generator
function and its shape rationale is documented in
`testbed/scripts/generate_traffic.py`.

## Feature schema

Columns in `flow_features.csv` (see `app/flow/features.py`, the single
source of truth both dataset building and inference read from):

| Column | Type | Description |
|---|---|---|
| `flow_key` | string | `{src}->{dst}:spi={spi}` — identifies the flow, not a training feature |
| `packet_count` | int | packets in the flow |
| `duration_s` | float | flow duration |
| `avg_packet_size`, `std_packet_size`, `min_packet_size`, `max_packet_size` | float | packet size distribution (bytes) |
| `avg_inter_arrival_ms`, `std_inter_arrival_ms` | float | inter-arrival time distribution |
| `bytes_per_second`, `packets_per_second` | float | throughput |
| `burstiness` | float | `(σ-μ)/(σ+μ)` over inter-arrival times (Goh & Barabási burstiness parameter) |
| `seq_gap_ratio` | float | fraction of non-consecutive ESP sequence numbers |
| `traffic_type` | string | **label** — parsed from the source pcap's filename |
| `source_pcap` | string | which pcap this row came from — metadata only, **not a training feature**, used solely to group train/test splits so flows from one capture never leak across the split |

## Train/test split methodology

**Grouped by source pcap, not by row** (`sklearn.model_selection.
GroupShuffleSplit`, 75/25 split, `random_state=42`). This prevents flows
from the same capture appearing on both sides of the split, which would
leak information and inflate apparent accuracy — see
`docs/technical_documentation.md` §5 and `app/ml/train.py`.

## Real training result (2026-09-02) — read the caveat, not just the number

`python -m app.ml.train` on the current 34-row dataset, `GroupShuffleSplit`
(75/25, grouped by `source_pcap`, `random_state=42`):

```
accuracy: 1.0
(precision/recall/f1 all 1.0 for every class present in the test split)
```

**This is a real number from real data, and it should not be quoted as
"the classifier's accuracy" without the rest of this paragraph.** The
held-out test split had only **10 rows total** (up from 7 before adding
the 5th config) — so this result says "the model perfectly separated all
6 classes on 10 examples," not "the model is 100% accurate."
With traffic-size signatures this distinct at this sample size (`video`
flows average ~1300 bytes/packet, `icmp` ~150-170, `email` ~1400-1500,
`web` ~130-230, `voip` ~254-266, `messaging` ~208-234 — see the raw values
in `data/datasets/flow_features.csv`), near-perfect separation on a
handful of examples is expected and does not demonstrate real-world
generalization. Report a number like this to judges only alongside this
caveat, or better, only after the dataset has grown enough for the test
split to contain a meaningful sample of every class.

## Known limitations

1. **Sample size.** 32 rows / 24 unique pcaps across 4 of 17 configs is
   real but small — see the training-result caveat above. This is the
   headline limitation now, not "no dataset exists" (that's resolved).
2. **Config coverage.** Only MODP-based configs are represented; the 6
   AES-GCM/ECP-DH configs don't negotiate on this Dockerfile's strongSwan
   build (see `backend/testbed/README.md`) and contribute zero rows.
   Since the ML classifier's target is traffic type, not config, this
   mainly limits how confidently "robust across configs" can be claimed
   (see the "Config matrix" section above), not classification itself.
3. `messaging` is an explicit approximation, not real captured traffic.
4. `voip`/`video`/`email` generators shape raw UDP traffic to match known
   packet-size/timing characteristics rather than running the literal
   application protocol.
5. Every capture so far used a short (15-20s) generator duration; longer
   runs would produce more, and more varied, flows per class.
